<p>In September 2024, our team consisting of <a href="https://www.linkedin.com/in/dhchan/">myself</a>, <a href="https://www.linkedin.com/in/kai-sng-hoo-081a3622a/">Kai Sng</a>, <a href="https://www.linkedin.com/in/yipkaimen/">Kai Men</a> and <a href="https://www.linkedin.com/in/wei-qi-chua/">Wei Qi</a> participated in a <a href="https://vcthackathon.devpost.com/?utm_campaign=vct-hackathon-esports-manager-challenge_20240725&amp;utm_content=draft_submission_saved&amp;utm_medium=email&amp;utm_source=transactional">hackathon</a> hosted by Devpost, AWS and Riot Games. The problem statement<strong> </strong>was to create an LLM-powered digital assistant that helps build teams and answers questions about VALORANT players.</p><p>When we first started, we had zero knowledge about the tools and technologies used. However, participating in this event is a transformative experience that pushed us beyond our comfort zone and accelerated our learning curve exponentially. In this article, I will share our journey building a VALORANT eSports digital assistant using Amazon Bedrock, despite having no prior experience with these technologies.</p><h3>Data Sources</h3><p>To use RAG, there must be data to retrieve. Our first step was to gather that data. Most data, such as player stats and tournament results, was sourced from Liquipedia. We called its API and pulled information that we needed into a readable format.</p><p>For subjective insights, such as regional playstyles, we relied on informal methods like watching matches, reading forums (<a href="http://vlr.gg/">VLR.gg</a>, VALORANT eSports’ Subreddit), and analysing content from creators like Airen. These insights were then organised and formatted into text for efficient model ingestion.</p><p>We ended up with 12 CSV and one Markdown file. The official S3 bucket provided (&gt;80GB) was not used due to its size and lack of useful information.</p><h3>Understanding RAG</h3><p>Next, we had to understand how RAG works. Retrieval Augmented Generation (RAG) combines traditional retrieval systems with generative AI. First, the system searches a knowledge base for relevant information related to the user’s query. Then it passes both the original query and the retrieved context to the LLM, allowing the model to generate responses grounded in specific data rather than just its training knowledge.</p><p>Next, we explored vector embeddings, a critical component of our RAG implementation. Vector embeddings convert text data (like player profiles, statistics, and game descriptions) into numerical representations in high-dimensional space. For our VALORANT assistant, we used these embeddings to transform player information into vectors where similar players or attributes would be positioned closer together mathematically.</p><p>When a user submits a prompt like “Find players who excel at clutch situations,” the system processes it through the same embedding model used for our source data, converting the query into the same high-dimensional vector space as our player information.</p><p>This query embedding captures the semantic meaning of “clutch performance” in the same mathematical space where our player data resides. The system then computes similarity scores (cosine similarity for our case) between the query vector and all vectors in our database.</p><p>For example, player profiles containing terms like “1v2 wins,” “high-pressure performance,” or “late-round effectiveness” would have embeddings mathematically closer to our query embedding. The system retrieves the most similar vectors based on these similarity scores, effectively finding the most relevant player information.</p><p>This approach allows the assistant to understand semantic relationships rather than just keyword matching. It can find relevant player information even when the exact phrasing differs, enabling more natural and effective information retrieval for team building recommendations.</p><h3>Tools and technologies</h3><p>We then came up with the relevant tools compatible with AWS:</p><ol><li>Data Source — S3 Bucket: All VALORANT player data is stored in an Amazon S3 bucket for centralized, scalable access.</li><li>Embedding Model — Cohere Embed English v3: Each data chunk is embedded using Cohere’s model via the Bedrock API, converting player statistics and profiles into vector representations. This model was selected for its strong semantic understanding of specialised gaming terminology while remaining cost-effective for production deployment.</li><li>Vector Database — Pinecone: The embedded vectors are stored in Pinecone, which provides efficient similarity search capabilities with low latency. This enables the system to quickly retrieve the most relevant player information based on semantic similarity rather than keyword matching.</li><li>LLM — Claude Haiku 3.0: We selected Haiku as our primary language model for generating responses. Its optimal balance of performance and cost made it suitable for real-time team building recommendations and player analysis while staying within budget constraints.</li><li>Front-end — Streamlit: For the user interface, we implemented a Streamlit application that provides an intuitive chat interface. We selected this as it can be written in Python — a language we are more familiar with.</li><li>Orchestration — AWS Bedrock Agents &amp; AWS Lambda: We implemented Lambda functions to handle processing logic and created API endpoints for seamless communication between our Streamlit front-end and backend systems. This allowed us to efficiently orchestrate the complex workflow from user query to response generation.</li></ol><p>We then combined all of our services into this architecture. Next, we discuss the exact methodology.</p><figure><img alt="" src="/blog/vct-esports-manager-hackathon-our-attempt/FxeISCiUAyeD0GKuaQIdLA.jpg" /><figcaption>Our Application Architecture</figcaption></figure><p>Next, I will elaborate more on each part of the architecture where necessary.</p><h3>Data Preprocessing and Chunking</h3><p>The chunking process is critical to ensuring that files are properly read and retrieved during the Retrieval-Augmented Generation (RAG) process. Here’s the breakdown:</p><p><strong>CSV Files</strong>: Each CSV file is chunked row by row. This ensures that each row is treated as a separate chunk, making it easier for the model to handle individual data points. For example, a larger file like vct-intl-amer-players.csv will be split into many CSVs like TenZ.csv (named after the player) with corresponding metadata files TenZ.csv.metadata.json (named after the CSV with a metadata tag as a JSON file). This ensures that each row can be retrieved later based on relevant queries.<br>An example of a metadata file is provided:</p><pre>{<br>    &quot;metadataAttributes&quot;: {<br>        &quot;standings&quot;: &quot;5th-6th&quot;,<br>        &quot;igl&quot;: &quot;false&quot;,<br>        &quot;region&quot;: &quot;Americas&quot;,<br>        &quot;league&quot;: &quot;vct international&quot;<br>    }<br>}</pre><p><strong>Markdown Files</strong>: These are chunked by headers to ensure proper sectioning. Each section under a header forms a chunk, and like the CSVs, each chunk is paired with a corresponding metadata file for easy retrieval.</p><p>None of AWS Bedrock’s chunking strategies provided the granularity we needed, as they couldn’t guarantee 1 chunk per row for CSV files. To overcome this, we implemented our own chunking method, ensuring that each CSV row became its own chunk with a corresponding metadata file. This gave us the control and precision required for accurate data retrieval during the RAG process.</p><h3>Action Group Logic</h3><p>The agent selects actions from a predefined <strong>Action Group</strong>, determining the appropriate steps to take based on the query type. For example, if the query is about player performance, the agent retrieves performance stats; if it’s about team composition, the agent retrieves role and team-based information.</p><p>The action group is defined in <a href="https://github.com/dhcchh/vct-hackathon-esports-manager/blob/main/src/bedrock-agent-action-group-openapi.yaml">this way</a>:</p><ul><li>This configuration is part of the <strong>action group</strong> responsible for selecting and retrieving the most relevant data chunks based on the conditions we set.</li><li>For example, if the prompt asks for players from game changers, an action group related to the Game Changers prompt will be initiated.</li><li>It uses a combination of metadata filters to refine the search and ensure that only specific results, such as players who were IGLs from a particular league and had top standings, are retrieved. This process ensures RAG returns the most suitable chunks for generating responses or building teams.</li></ul><h3>Retrieval with Lambda Functions</h3><ul><li>While the agent orchestrates which tasks need to happen, it relies on Lambda functions to perform the heavy lifting — particularly when it comes to <strong>retrieving relevant information</strong> from a <strong>Vector Database (VDB).</strong></li><li>Each action group has a set of <strong>Lambda functions</strong> associated with it, each one custom-built for a particular job. These jobs could include searching for similar vectors in the VDB, pulling data from other sources, or performing data transformations to prepare the best response context.</li><li>The Lambda function then retrieves these <strong>vectors</strong> (representing information, context, or past knowledge related to the prompt) and sends them to the LLM. This context helps the LLM generate a response that’s well-informed and aligned with the user’s needs.</li></ul><h3>Challenges we ran into</h3><ol><li>The first challenge involved chunking the CSV files. The factors we considered was the structured nature of CSV data, which would be lost with most predefined chunking strategies predefined in AWS.<br>Since we needed each row in the CSV file to represent a single chunk, we had to write additional scripts to handle this manually. This added complexity to the data processing workflow but was necessary to ensure the model received the data in the correct format.</li><li>The second challenge was with metadata in Pinecone. Upserting data through the console didn’t work because the metadata fields weren’t being read correctly, preventing the model from filtering data based on metadata.<br>To solve this, we had to write more scripts to upsert and embed data without using the console, adding another layer of scripting to the project. We used the boto3 library in Python to help us interact with the AWS services needed.</li></ol><h3>Learning Outcomes</h3><p>Our hackathon journey taught us invaluable lessons across multiple dimensions:</p><ul><li>Built a complete RAG system and mastered AWS ecosystem — From document chunking to retrieval optimization, we gained hands-on experience with S3, Lambda, IAM and Bedrock services, creating a cohesive architecture that would have taken months to learn conventionally.</li><li>Applied domain knowledge to AI development — Translating VALORANT esports expertise into structured data and effective prompts required bridging technical implementation with actual recruitment needs, resulting in a genuinely useful product.</li><li>Balanced technical constraints with business requirements — We continuously navigated tradeoffs between model performance, cost efficiency, and user experience, learning to make pragmatic decisions under time pressure.</li></ul><p>The project demonstrated how combining technical skills with domain expertise is crucial for developing AI solutions that solve real problems rather than merely showcasing technology.</p><h3>Conclusion</h3><p>Although we did not win (or even make it to the finals), we learnt a lot by participating. We got exposed to a use case of GenAI in eSports, and how these technologies can be effectively deployed on cloud platforms like AWS or even on-premise solutions.</p><p>The practical experience we gained has expanded our skills and deepened our understanding, driving us to further explore these fields. We’re excited to apply this knowledge in future projects, pushing the limits of AI-driven solutions and discovering new, innovative applications.</p><p>Thank you for reading!
